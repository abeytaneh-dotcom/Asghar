## آزمایش مسیر فروش واقعی در دیتابیس آزمایشی

- بکاپ SQL Server از دیتابیس `1405` با `BACKUP ... WITH CHECKSUM` روی همان کامپیوتر گرفته شد و با `RESTORE VERIFYONLY` صحت‌سنجی شد.
- دیتابیس ایزوله `TehranBridgeSandbox1405` از همان بکاپ بازیابی شد.
- در نسخه کپی‌شده، `EShop_FactorInsert` و `EShop_FactorDetailInsert` سفارش و ردیف فروش را ایجاد کردند.
- `Sodor_Factor` فاکتور نهایی ایجاد کرد و موجودی نمونه از **۹ به ۸** کاهش یافت؛ آزمون اولیه داخل تراکنش Rollback شد.
- ماژول واقعی `PyramidBridge.ps1` در Sandbox فاکتور آزمایشی ثبت کرد؛ اجرای دوباره فاکتور تکراری نساخت.
- HTML فاکتور سازگار با چاپگر ۸۰ میلی‌متری در `D:\TehranBridge\receipts` ساخته شد. **چاپ فیزیکی آزمایش نشده است.**
- SQL Server عملیاتی `1405` به‌جز عملیات BACKUP و خواندن، تغییر نداد؛ فاکتور آزمایشی فقط در کپی اجرا شد.

## سایت و API

- نسخه عمومی `https://tehranmarket-baharestan.ir/pyramid_api.php?action=status` از سیستم پیرامید با پاسخ `401` و هدر `X-Tehran-Sync-Version: 2` در دسترس بود؛ این **تأیید اتصال احرازشده نیست**.
- سمت سایت، API جدید در شاخه توسعه تنها با کلید معتبر و فایل تنظیمات محافظت‌شده اجازه نوشتن می‌دهد.
- `snapshot_batch` بسته‌های داده را فقط در جدول Staging دریافت می‌کند.
- `snapshot_finalize` پس از تطبیق کامل تعداد و بارکدها، قیمت و موجودی را **اتمیک** در یک تراکنش به‌روز می‌کند و سفارش‌های هنوز تحویل‌داده‌نشده به پیرامید را از موجودی قابل فروش کسر می‌کند.
- کالای فعال سایت که در اسنپ‌شات پیرامید تطبیق ندارد پس از نهایی‌سازی با **موجودی قابل فروش صفر** باقی می‌ماند (بدون حدس یا تغییر عنوان/قیمت).
- در حالت فعال، آخرین اسنپ‌شات اگر بیش از **۱۸۰ ثانیه** قدیمی باشد، ثبت سفارش جدید سایت Fail-closed خواهد بود.
- آزمون ایزوله GitHub **43967201935** موارد بالا را روی بازیابی SQL شامل ۱۸ جدول و ۹٬۸۴۹ محصول پاس کرده است.
- آزمون امنیتی PHP و کد مخزن در GitHub Actions جداگانه اجرا شده است.

## وضعیت دسترسی و قفل فعال‌سازی

- ریموت دسکتاپ هر دو کامپیوتر متصل است؛ ارتباط مستقیم شبکه USB بین آن‌ها لازم نیست.
- `D:\TehranBridge\PyramidBridge.ps1` نصب شده و Audit و SandboxTest موفق‌اند.
- پیکربندی اصلی ویندوز **غیرفعال و آزمایشی** است؛ فایل پیکربندی مجزای تولیدی با `enabled=false`, `allow_live_pos_writes=false`, `allow_live_catalog_writes=false` ساخته شده است.
- کلید وب‌سایت در انتقال رمزگذاری‌شده (RSA-OAEP-SHA256) شناسایی شد؛ **احراز هویت واقعی از کامپیوتر پیرامید هنوز با این کلید تأیید نشده است** و کلید محرمانه در GitHub/گزارش‌ها قرار نگرفته است.
- `TEHRANMARKET_CPANEL_TOKEN` در آخرین بررسی GitHub Actions موجود نبود؛ FTPS موجود است.
- **هیچ کدام از تغییرات API یا موجودی این شاخه روی سایت زنده Deploy نشده‌اند.**

## گیت‌های مانده پیش از فروش واقعی

1. گرفتن بکاپ تازه از وضعیت **امروز** دیتابیس و فایل‌های سایت؛ آزمایش بازیابی جداگانه.
2. انجام تطبیق کالا با دیتابیس فعلی سایت؛ ۱۰۴ کالای نامنطبق تا زمان تأیید دستی غیرقابل سفارش شوند.
3. تأیید مسیر ارسال کلید اتصال به ویندوز و تست `status` و `orders` احرازشده.
4. اجرای استقرار محدود و قابل Rollback از نسخه سایت همراه با migration آزمایش‌شده؛ تطبیق فایل `shop.php` زنده با شاخه توسعه (تفاوت نسخه تأیید شده).
5. آزمایش نهایی‌سازی فاکتور، رزرو و چاپ روی سفارش آزمایشی مورد توافق؛ بازپرداخت، لغو سفارش، هزینه ارسال و تخفیف هم باید پیش از پذیرش همه سفارش‌ها تعیین تکلیف شوند.
6. پس از تست موفق و کنترل نسخه فعلی، راه‌اندازی Agent خروجی HTTPS به‌صورت زمان‌بندی‌شده روی دستگاه پیرامید با پایش heartbeat و هشدار قطعی.

**قانون اجرا:** بدون انجام گیت‌ها، نه فایل‌های زنده سایت و نه دیتابیس عملیاتی پیرامید تغییر داده نمی‌شوند.


## اقدامات اجرایی جدید (ادامه ۱۷ نوامبر ۲۰۲۶)

- ارتباط ریموت دو دستگاه بررسی شد؛ \`DESKTOP-KPRT310\` و \`EXSOM-J3\` آنلاین بودند.
- نسخه کاندید Bridge به شاخه و پوشه FTPS خصوصی \`__tm_pyramid_bridge_candidate_20261117\` منتقل و PHP lint و دسترسی مسدود \`403\` آن تأیید شد. GitHub Actions: \`43972203616\`.
- **بکاپ تازه فقط از فایل‌های کد اصلی سایت** در پوشه محافظت‌شده \`__tm_predeploy_php_backup_20261117\` با \`403\` و PHP lint موفق ایجاد شد. GitHub Actions: \`43972858211\`.
- آزمایش اتصال خارجی به MySQL فعلی نشان داد تنظیمات آن **server-local** است: \`LIVE_DB_NETWORK=SERVER_LOCAL_ONLY\`. در نتیجه با حساب FTPS موجود، **بکاپ تازه دیتابیس تولید نشد**. GitHub Actions: \`43972844914\`.
- به‌جای جایگزینی کل \`shop.php\`، روی نسخه واقعی فایل زنده فقط محافظت زمان آخرین Sync افزوده شد و همه توابع جاری \`store_lib.php\` نگه داشته شدند. این نسخه در \`__tm_pyramid_surgical_merge_candidate_20261117\` نگهداری و \`403\` تایید شد. GitHub Actions: \`43973345152\`.
- همین فایل \`shop.php\` جراحی‌شده در یک محیط مستقل با دیتابیس بکاپ‌شده ۹٬۸۴۹ کالایی اجرا شد و HTTP \`200\`، عملیات اتمیک Snapshot، کسر رزرو سفارش، جلوگیری از replay، و شروط بسته‌شدن Checkout در صورت Sync قدیمی، همگی موفق بودند. GitHub Actions: \`43973839191\`.
- در پردازش سفارش ویندوز، ذخیره فاکتور ۸۰ میلی‌متری **قبل از** \`order_ack\` قرار گرفت تا اگر تولید فایل چاپی مشکل داشت، سفارش سایت به‌اشتباه «انتقال‌یافته» نشود.
- برای جلوگیری از دوبار ثبت‌شدن سفارش‌های تاریخی، \`SyncOnce\` در دیتابیس عملیاتی تا وجود و اعتبارسنجی فایل \`D:\TehranBridge\site_orders_start_after_id.txt\` **قفل** می‌ماند. سفارش‌های قدیمی‌تر از مرز تأییدشده برای بررسی نگهداری می‌شوند؛ این مرز نباید حدسی تعیین شود.
- اجرای Sandbox و Audit بعد از این تغییرات دوباره موفق بود؛ GitHub CI امن روی شاخه توسعه، اجرای \`43974518653\`، موفق.
- Task ویندوز \`TehranMarket-PyramidBridge\` موجود اما **Disabled** است. وظایف خواندنی Snapshot، تطبیق و Inbox چاپی وجود دارند. گزارش Inbox در آخرین مشاهده: \`ORDER_PULL=DISABLED_NO_SITE_SECRET\`.
- مسیر کلید اتصال سایت روی ویندوز هنوز آماده استفاده نیست؛ کد امنیتی سایت از طریق پاسخ \`401\` مشاهده شد، اما \`status\` با هدر معتبر از دستگاه پیرامید تأیید نشده است.
- **هیچ deploy عمومی روی سایت، هیچ تغییر موجودی عملیاتی در SQL Server و هیچ ثبت فروش واقعی انجام نشده است.**

### شروط باقی‌مانده برای روشن‌کردن Sync واقعی

۱. دریافت بکاپ **تازه دیتابیس زنده MySQL از داخل cPanel** و آزمایش بازگردانی همان بکاپ، به‌علاوه نسخه کد تازه ذخیره‌شده.
۲. اتصال معتبر API سایت از دستگاه پیرامید با کلید محافظت‌شده، بدون انتشار رمز یا کلید در لاگ/گیت‌هاب.
۳. بررسی سفارش‌های تاریخی و ثبت مرز شروع صحیح تا فروشی در پیرامید دوبار ثبت نشود.
۴. بررسی اختلاف ۱۰۴ بارکد سایت و وضعیت پرداخت/هزینه ارسال/تخفیف؛ سفارش غیرقابل تطبیق باید صف بررسی دستی داشته باشد.
۵. استقرار پله‌ای API و جداول Snapshot با نسخه کنترل‌شده، اجرای حالت آزمایشی و تست چاپ روی رسید فیزیکی.
۶. سپس و فقط پس از قبول موارد بالا، فعال‌کردن تنظیمات و Task زمان‌بندی‌شده ویندوز.

این گزارش فقط شواهد عملی را ثبت می‌کند و ادعای تکمیل اتصال تولیدی ندارد.
