**وضعیت:** کدنویسی صرفاً در شاخه آزمایشی `feature/enterprise-v3`؛ **منتشرنشده و تأییدنشده برای تولید**.
**مبدأ:** `websaza-hosting`، کامیت `0e6991143794dcce393c735bb43407e1e83e0900`.
**محیط آزمایش:** GitHub Actions فقط برای lint و آزمون استاتیک؛ بدون تماس با cPanel، پایگاه داده، درگاه یا پیرامید.

## یافته‌های تأییدشده از سورس

1. `index.php` هنگام درخواست عادی، `ts_seed_pyramid_1400()` را فراخوانی می‌کرد.
2. `pyramid_seed_1400.php` توان تغییر موجودی کالاها به ۱۰ و بازنویسی مشخصات کاتالوگ را داشت.
3. `schema.php` امکان تولید خودکار بارکد و مقداردهی موجودی دمو و تغییر DDL داشت.
4. صفحات فروشگاه، پنل مدیر، AI، پرداخت و بعضی APIها در جریان HTTP تابع‌های `ensure_product_schema` و/یا سایر schema-helperها را اجرا می‌کردند.
5. `index.php` فایل `product_image_seed.php` را اجرا می‌کرد که می‌توانست تصاویر محصول را تغییر دهد.
6. API پیرامید قابلیت تغییر قیمت و موجودی داشت، اما هنوز مستندات رسمی نرم‌افزار صندوق و آزمون احراز منبع داده‌ها موجود نیست.
7. کلید همگام‌سازی می‌توانست هنگام درخواست وب تولید شود و صفحه مدیر مقدار آن را نمایش می‌داد.
8. `.htaccess` برخی فایل‌های حساس را می‌بست، اما فهرست کامل فایل‌های setup/seed/migration را شامل نمی‌شد.
9. `uploads/.htaccess` از قبل اجرای مستقیم پسوندهای اسکریپتی متداول را محدود کرده بود.
10. بخشی از احراز هویت مدیر و کنترل CSRF در کد فعلی وجود دارد؛ سطح پوشش سراسری، 2FA، rate limit و OWASP ASVS هنوز ارزیابی عملی کامل نشده‌اند.

## تغییرات انجام‌شده روی شاخه آزمایشی

- `index.php`: حذف Seed خودکار و جهش تصاویر در درخواست GET.
- `install.php`: بازنشسته‌سازی نصب‌کننده HTTP و مسدودکردن اجرا.
- `pyramid_seed_1400.php`: حذف کد تغییر محصولات/موجودی؛ جایگزینی با ماژول غیرفعال و غیرمخرب.
- `schema.php`: بازنشسته‌کردن تولید بارکد/موجودی پیش‌فرض و حذف فراخوانی mapping خودکار. توابع DDL باقی‌مانده فقط باید در migration کنترل‌شده و جداگانه فراخوانی شوند.
- حذف invocationهای `ensure_product_schema`, `ts_admin_schema`, `ts_coupon_schema`, `ts_ai_learning_schema`, `ts_sync_ensure_schema`, `ts_schedule_auto_backup` از مسیرهای HTTP بازبینی‌شده.
- `pyramid_api.php`: حالت فقط‌خواندنی پیش‌فرض؛ `product_update`, `products_batch`, `order_ack` فعلاً HTTP 403 می‌دهند. مسیرهای احراز هویت‌شده خواندن وضعیت و کاتالوگ محفوظ‌اند.
- `pyramid_sync_lib.php`: حذف ساخت خودکار کلید از جریان HTTP؛ اگر کلید از پیش وجود نداشته باشد، API بسته می‌ماند.
- `pyramid.php`: عدم ایجاد کلید جدید هنگام بازکردن پنل و عدم نمایش مقدار کلید، فقط وضعیت «موجود است/تنظیم نشده».
- `.htaccess`: محافظت افزوده برای فایل‌های خصوصی، seed و فایل‌های نسخه پشتیبان.
- `tests/test_phase1_safety.py`: آزمون استاتیک مسیرهای خطرناک.
- `bin/preflight.php`: ابزار preflight صرفاً CLI با شرط staging و تراکنش فقط‌خواندنی.
- `.github/workflows/tehran-phase1-security-ci.yml`: بررسی مستقل PHP syntax و آزمون استاتیک، بدون دسترسی و انتشار محیط عملیاتی.

## Migration و بازگشت

- **Migration دیتابیس اعمال‌شده: هیچ**. این مرحله فقط کد در شاخه مجزا را تغییر داده است.
- بازگشت پیش از ادغام: حذف یا کنارگذاشتن شاخه `feature/enterprise-v3`؛ شاخه اصلی و وب‌سایت زنده هیچ تغییری نکرده‌اند.
- پیش از استفاده از این تغییرات روی staging، یک کپی دیتابیس تهیه و restore آن آزمایش شود؛ سپس پیش‌نیاز جدول‌ها/ستون‌ها با نسخه هدف مقایسه شود.
- ساخت migration نسخه‌بندی‌شده و rollback جداگانه باقی است. حذف schema auto-init بدون مهاجرت اولیه روی دیتابیس ناقص موجب fail-closed/خطای برنامه می‌شود.
- در صورت استقرار آینده، بازگشت کد از snapshot/commit پیشین انجام شود و بازگشت دیتابیس فقط طبق نسخه پشتیبان بررسی‌شده و تأیید انسانی مجاز است.

## نیازمندی‌های مدیر بدون مقدار محرمانه

1. معرفی محل **staging** و مجوز فقط برای تهیه نسخه پشتیبان در همان محیط.
2. تأیید موفقیت بازیابی نسخه پشتیبان و بررسی فضای هاست و محدودیت CPU/RAM/MySQL/Cron.
3. ارائه مستندات رسمی پیرامید شامل واحد پول، بارکد و API/خروجی استاندارد.
4. پیش از تولید: تأیید لاگ‌های سناریوهای ورود/سفارش/پرداخت/لغو/مرجوعی و عدم تغییر ظاهر/AI/بارکدخوان.
